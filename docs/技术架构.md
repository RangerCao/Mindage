## 二、核心类设计

### LightRAG 主类

LightRAG 采用 **多继承 Mixin 模式** 将一个庞大的类拆分为可维护的模块：

```python
class LightRAG(_RoleLLMMixin, _StorageMigrationMixin, _PipelineMixin):
    """主类是一个 @final dataclass"""
```

#### Mixin 职责分工

| Mixin | 文件 | 职责 |
|-------|------|------|
| `_PipelineMixin` | `pipeline.py` | 文档处理全流程：解析 → 分块 → 提取 → 合并 |
| `_RoleLLMMixin` | `llm_roles.py` | 4 个 LLM 角色注册、配置、运行时调度 |
| `_StorageMigrationMixin` | `storage_migrations.py` | 数据结构版本迁移 |

#### 状态机

```
NOT_CREATED → __post_init__ → CREATED
    → initialize_storages() → INITIALIZED
    → finalize_storages()   → FINALIZED
```

`__post_init__` 阶段自动创建 **12 个存储实例**，涵盖 full_docs、text_chunks、full_entities、full_relations、entities_vdb、relationships_vdb、chunks_vdb、graph、llm_response_cache、doc_status 等。

## 三、文档处理流水线

```
  Upload
    │
    ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  1. File Extraction                                         │
  │     • 确定解析引擎（legacy / mineru / docling / native）    │
  │     • 解析文件名 hint（如 document.[mineru].pdf）            │
  │     • 遵循 LIGHTRAG_PARSER 环境变量规则                      │
  └─────────────────────────────────────────────────────────────┘
    │
    ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  2. Parsing（内容解析）                                      │
  │     • legacy：同步提取（pypdf / python-docx / 文本解码）    │
  │     • mineru：HTTP 调用 MinerU 服务（多模态 OCR）            │
  │     • docling：HTTP 调用 Docling 服务（IBM 引擎）            │
  │     • native：原生 .docx 解析                                │
  │     • 结果持久化到 full_docs（KV Storage）                   │
  └─────────────────────────────────────────────────────────────┘
    │
    ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  3. Chunking（文本分块）                                     │
  │     • Fix：固定 token 长度                                   │
  │     • Recursive：递归分隔符分块（LangChain）                 │
  │     • Vector：语义相似度分块（LangChain）                    │
  │     • Paragraph：段落语义分块                                │
  │     • 结果存入 text_chunks（KV Storage）                     │
  └─────────────────────────────────────────────────────────────┘
    │
    ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  4. KG Extraction（知识图谱提取） ❮── 调用 LLM ──╮          │
  │     • 对每个 chunk，LLM 提取实体和关系              │          │
  │     • 实体：名称、类型、描述                        │          │
  │     • 关系：源实体、目标实体、关键词、描述           │          │
  │     • 支持 JSON 格式输出（稳定）或文本输出（快速）   │          │
  └─────────────────────────────────────────────────────────────┘
    │
    ▼
  ┌─────────────────────────────────────────────────────────────┐
  │  5. Merging（合并到全局图谱）                                │
  │     • Phase 1: 实体去重合并（同名实体聚合描述）              │
  │     • Phase 2: 关系去重合并（同源目标关系聚合）              │
  │     • Phase 3: 更新向量存储（实体 + 关系 + 文本块嵌入）     │
  │     • 写入图存储（NetworkX / Neo4j）                         │
  └─────────────────────────────────────────────────────────────┘
    │
    ▼
  Completed
```

### 并发控制

流水线使用 **pipeline_status**（进程内共享字典 + 命名空间锁）协调并发：

| 字段 | 含义 | 互斥规则 |
|------|------|----------|
| `busy` | 流水线繁忙 | 不阻塞 enqueue |
| `destructive_busy` | 删除操作中 | 阻塞 enqueue |
| `scanning` | 扫描任务中 | 阻塞重复扫描 |
| `scanning_exclusive` | 扫描分类阶段 | 阻塞 enqueue |
| `pending_enqueues` | 等待中的上传 | 扫描会等待 |

允许 **并发 enqueue + processing**：上传的文档在 `doc_status` 落地，流水线循环结束后检查 `request_pending` 标志，自动拾取新任务。

## 四、四角色 LLM 架构

LightRAG 将 LLM 调用分为 4 个独立角色，可各自绑定不同的模型和配置：

```
                    ┌─────────────────────────┐
                    │     ROLES 注册表         │
                    │  RoleSpec(name, desc)    │
                    └────────┬────────────────┘
                             │
         ┌───────────────────┼───────────────────┐
         ▼                   ▼                   ▼
   ┌──────────┐      ┌──────────────┐     ┌──────────┐
   │ EXTRACT  │      │   KEYWORDS   │     │  QUERY   │
   │ 实体/关系 │      │  关键词提取  │     │ 回答问题  │
   │ 提取     │      │              │     │          │
   │ 强模型   │      │  轻量模型    │     │  强模型   │
   └──────────┘      └──────────────┘     └──────────┘

                    ┌──────────┐
                    │   VLM   │
                    │ 多模态   │
                    │ 图像分析  │
                    └──────────┘
```

每个角色的配置通过 `resolve_role_llm_settings(role_name)` 读取环境变量：

```ini
# 角色专用配置前缀
LLM_BINDING_EXTRACT=openai
LLM_MODEL_EXTRACT=gpt-4o
LLM_BINDING_KEYWORDS=openai
LLM_MODEL_KEYWORDS=gpt-4o-mini
```

也可以在初始化时通过 `RoleLLMConfig` 传入。

## 五、查询引擎

### 五种查询模式

```
用户查询
    │
    ├──→ local  ──→ 局部实体检索（KG 邻居节点）
    │      返回：实体 + 直接关系 + 相关文本块
    │
    ├──→ global ──→ 全局关系检索（KG 关系链）
    │      返回：关系 + 间接关联实体 + 文本块
    │
    ├──→ hybrid ──→ local + global 结果合并
    │
    ├──→ naive  ──→ 纯向量检索（不使用 KG）
    │      返回：文本块
    │
    └──→ mix    ──→ local + global + naive 结果合并（推荐）
```

### 查询流程

```
Query
  │
  ├─ 1. 向量/图谱检索（top_k 实体 + chunk_top_k 文本块）
  │
  ├─ 2. Token 预算控制
  │     MAX_ENTITY_TOKENS + MAX_RELATION_TOKENS
  │     + Chunk_Tokens ≤ MAX_TOTAL_TOKENS
  │
  ├─ 3. 重排序（可选 Reranker）
  │
  ├─ 4. 构建 Prompt（实体+关系+文本块 → 上下文）
  │
  └─ 5. LLM 生成回答（支持流式输出）
```

## 六、存储层架构

### 四类存储

```
LightRAG 实例
    │
    ├── KV Storage ──────────────── 文本/缓存数据
    │   ├── full_docs             原始文档内容
    │   ├── text_chunks           分块结果
    │   ├── full_entities         实体数据
    │   ├── full_relations        关系数据
    │   ├── entity_chunks         实体关联的块
    │   ├── relation_chunks       关系关联的块
    │   └── llm_response_cache    LLM 响应缓存
    │
    ├── Vector Storage ──────────── 向量嵌入
    │   ├── entities_vdb          实体向量
    │   ├── relationships_vdb     关系向量
    │   └── chunks_vdb            文本块向量
    │
    ├── Graph Storage ───────────── 知识图谱结构
    │   └── chunk_entity_relation_graph  实体-关系图
    │
    └── Doc Status Storage ──────── 文档处理状态
        └── doc_status            PENDING / PARSING / PROCESSING / PROCESSED / FAILED
```

### 存储实现矩阵

| 实现 | KV | Vector | Graph | DocStatus | 特点 |
|------|:--:|:------:|:-----:|:---------:|------|
| JSON 文件 | ✅ | - | - | ✅ | 默认，开发调试 |
| NanoVectorDB | - | ✅ | - | - | 纯 Python，轻量 |
| NetworkX | - | - | ✅ | - | 内存图谱，支持 GraphML |
| PostgreSQL | ✅ | ✅ (pgvector) | - | ✅ | 统一存储 |
| MongoDB | ✅ | ✅ | ✅ | ✅ | 统一存储 |
| OpenSearch | ✅ | ✅ | - | ✅ | 统一存储 |
| Neo4j | - | - | ✅ | - | 专业图数据库 |
| Memgraph | - | - | ✅ | - | 高性能内存图 |
| Milvus | - | ✅ | - | - | 专业向量库 |
| Qdrant | - | ✅ | - | - | 向量+Payload分区 |
| Redis | ✅ | - | - | - | 高速缓存 |
| FAISS | - | ✅ | - | - | Meta 向量库 |

### Workspace 数据隔离

通过 `workspace` 参数实现数据隔离，不同实现方式不同：

- **文件存储**：`{working_dir}/{workspace}/` 子目录
- **集合存储**：collection name 前缀
- **关系型**：workspace 列过滤
- **Qdrant**：payload 分区

## 八、关键设计模式

### 1. 代理模式（Proxy）

`_RAGProxy` 包装 `LightRAG` 实例，所有路由通过代理访问。切换工作区时只换代理背后的实例，路由无需重建。

### 2. 插件化存储（Strategy Pattern）

每种存储类型通过 `STORAGE_IMPLEMENTATIONS` 注册表注册，`get_storage_class()` 工厂方法解析。

### 3. 多角色 LLM 路由（Registry + Factory）

`ROLES` 注册表定义了 4 个角色，`_RoleLLMMixin` 提供运行时注册和配置更新。

### 4. 异步并发控制（Semaphore + Queue）

每个 LLM 角色有独立的 `asyncio.Semaphore` 控制并发，文档处理有 3 个队列（parse / analyze / insert）。

### 5. 重试与容错（Tenacity）

所有 LLM 调用和存储操作均包装了 tenacity 重试策略，支持指数退避。
